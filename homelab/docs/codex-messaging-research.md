Purpose: assess phone messaging interfaces for Codex on the management VM before choosing a design or implementation.

# Codex messaging gateway research

Researched 2026-11-13. This is research and proposed design, not an accepted ADR or deployment authorization. No bridge was installed, account connected, or infrastructure changed. Local inspection was limited to public instructions, Git status, and CLI version/help; credential stores, inventories, and private repositories were not inspected.

## Recommendation

**Recommend Telegram private-chat Bot API long polling for a one-person messaging gateway on the Linux management VM**, provided Simon accepts Telegram cloud-chat privacy and a deliberately limited execution identity. Pair it with a local Codex app-server interface. This is a design conclusion: Telegram supplies official polling without an inbound listener; WhatsApp uses a business platform and webhooks; SMS adds carrier costs and a poor interface for long interactive work. Slack and Discord also support outbound connections and are credible alternatives, so “no public ingress” alone does not uniquely favour Telegram. Sources and tradeoffs follow.

The recommendation changes if end-to-end encryption or continuity with the *existing desktop conversation and connected tools* is essential. Evaluate Matrix with a properly encrypted client for the former, and first-party ChatGPT remote connections for the latter. The latter currently requires a supported Mac/Windows desktop host, even when work runs on an SSH host. It is not documented as phone-to-standalone-Linux-CLI setup. [Remote connections](https://learn.chatgpt.com/docs/remote-connections)

## Channel comparison: verified capabilities and design judgments

| Channel | Verified capability | Judgment for this homelab |
| --- | --- | --- |
| **Telegram** | Official Bot API has `getUpdates` long polling; bot registration uses BotFather. Polling and webhooks are mutually exclusive. [Bot API](https://core.telegram.org/bots/api#getupdates), [Bot FAQ](https://core.telegram.org/bots/faq) | Best default for a small personal chat interface: no business account or public webhook relay needed. Requires a Telegram account, bot token, explicit sender authorization, and acceptance of the privacy limitation below. |
| **Discord** | Apps open secure outbound Gateway WebSockets, maintain heartbeats/session state, and reconnect or resume. Gateway intents govern events and message content; privileged intents need configuration and sometimes review. [Gateway](https://docs.discord.com/developers/events/gateway) | Strong runner-up if Simon already uses Discord. A dedicated app/bot and restricted DM or private channel are necessary design choices; authorization must use account IDs, not channel visibility alone. More connection lifecycle work than Telegram polling. Do not claim small personal bots necessarily need verification. |
| **Slack** | Socket Mode delivers events and interactive payloads without a public HTTP URL. Setup creates an app, enables Socket Mode, and generates an app-level token; sending messages also uses a bot token. Connections refresh and must be replaced. [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) | Equally viable without ingress, especially for an existing personal workspace. Workspace/app installation, scopes, and multiple tokens add administration for one user. Prefer it if its existing workspace and interaction UI outweigh Telegram's simpler setup. |
| **Matrix** | The client-server specification provides `/sync` with timeout/since tokens and encrypted-room APIs, device verification, key sharing, and key backup. It warns that key sharing must be handled carefully. [Client-server specification](https://spec.matrix.org/latest/client-server-api/) | Best candidate if encryption/control outweigh simplicity. Use an established encryption-capable SDK, persist its crypto store, and test device verification/recovery. Encryption ends at the gateway, where Codex needs plaintext. A hosted homeserver permits outbound client access; self-hosting adds another service and phone-access decision. No multi-agent bus is required. |
| **Signal** | `signal-cli` describes itself as unofficial, offers JSON-RPC/daemon interfaces, and warns that releases over three months old may fail against server changes. [Project README](https://github.com/AsamK/signal-cli) | Interesting privacy-oriented alternative, but not an official supported bot API established by this research. Account linking/registration and continual compatibility maintenance make it a weaker low-maintenance choice. |
| **WhatsApp** | Official Cloud API sends from a business phone identity; incoming messages arrive through configured webhooks. Account/app permissions and access tokens are involved. [Platform overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/overview), [Webhooks](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/overview) | Poor fit for the current no-inbound design: requires an approved external relay or a newly accepted ingress architecture. Do not automate an ordinary personal account using an unofficial linked-device workaround as the baseline. Business onboarding and policy applicability remain blockers. |
| **SMS** | A representative provider, Twilio, exposes inbound messages through webhooks and a message resource. Long bodies split into chargeable segments. Costs include phone-number rental, sent/received messages and carrier fees, varying by destination/type. [Message resource](https://www.twilio.com/docs/messaging/api/message-resource), [Pricing](https://www.twilio.com/en-us/pricing/messaging) | Good fallback notification channel; weak primary interface for diffs, progress and scoped approvals. A polling design using the provider API is possible, but requires its own delivery cursor and authorization design. Number ownership is insufficient assurance for powerful administration. No exact prices are assumed. |
| **ntfy** | Subscription supports HTTP streaming, polling and WebSockets. Notification buttons can open a URL or issue an HTTP request. [Subscription API](https://docs.ntfy.sh/subscribe/api/), [Actions](https://docs.ntfy.sh/publish/#action-buttons) | Reuse existing alerting for “task finished/needs attention” if desired. Turning topics and buttons into a full authenticated chat/approval client is additional application work; it does not automatically supply conversation semantics. |
| **First-party remote connections** | Mobile can continue chats, steer, answer questions, approve actions and inspect output using a connected host's projects/tools. Supported mobile setup starts in the Mac/Windows desktop app; an SSH project can run on a remote host through that app. A relay avoids exposing the host publicly. [Remote connections](https://learn.chatgpt.com/docs/remote-connections) | Evaluate first if “control Codex from my phone” matters more than “message a Telegram bot.” Preserves the host environment better than a new gateway. Adds a desktop host dependency; it is a different interface from Telegram/WhatsApp/SMS. |

**WhatsApp policy uncertainty:** the official terms search result currently restricts primary general-purpose AI functionality and describes regional exceptions; opening the terms redirected to a login page. This is not enough to determine whether a private personal Codex controller qualifies. Do not assert either universal prohibition or permission. Resolve current terms, number region and use-case eligibility before adopting it. Pricing and customer-service-window rules also need rechecking against accessible current Meta documentation; this research does not promise free replies. [Official business solution terms](https://www.whatsapp.com/legal/business-solution-terms/)

## Codex integration: version matters

Local read-only checks returned **`codex-cli 0.146.0`**. Its help labels app-server experimental and exposes stdio, Unix socket, WebSocket and off transports. The matching release documentation provides initialization, thread start/resume/read, turn start/steer/interrupt, streamed events and approval requests. `turn/steer` targets an expected active turn; interrupt is cancellation, not a rollback. Some APIs/fields are gated experimental. Prefer stdio between bridge and its own child process; a Unix socket may suit an independently supervised server. Avoid a network app-server listener. Generate protocol schemas from the *chosen installed binary* during implementation and pin compatibility. [0.146.0 app-server README](https://github.com/openai/codex/blob/rust-v0.146.0/codex-rs/app-server/README.md)

OpenAI recommends app-server for rich custom clients and SDKs for automation. At the matching release, TypeScript SDK execution spawns `codex exec --experimental-json` and uses `exec resume` for a thread; it is not simply an interactive approval client. `codex exec` is appropriate for predefined noninteractive jobs, with explicit permissions and streamed JSON, rather than a full phone conversation UI. [App-server guide](https://developers.openai.com/codex/app-server/), [TypeScript execution source](https://github.com/openai/codex/blob/rust-v0.146.0/sdk/typescript/src/exec.ts), [Noninteractive guide](https://developers.openai.com/codex/noninteractive/)

**Challenge to a DIY RPC implementation:** current official docs also offer a stable Python SDK that controls app-server and ships a pinned CLI runtime. Some currently documented features require CLI 0.151.0 or 0.166.0. Therefore compare a version-compatible SDK against hand-written JSON-RPC before selecting a language; do not install the latest SDK and assume it uses local 0.146.0. A matching-release Python package manifest pins its own runtime. [SDK guide](https://developers.openai.com/codex/sdk/), [0.146.0 Python package manifest](https://github.com/openai/codex/blob/rust-v0.146.0/sdk/python/pyproject.toml)

Current authentication docs distinguish ChatGPT subscription access from separately billed Platform API-key usage, recommend API keys for programmatic workflows, and describe headless device-code login as beta. Subscription use remains subject to account/workspace eligibility, model availability and limits; no unlimited or zero-incremental-cost promise follows. Choose authentication and spending limits explicitly. Login/cache handling belongs to an operator on the host, never a messaging conversation. [Authentication](https://developers.openai.com/codex/auth/)

A newly launched VM app-server supplies its own configured tools, filesystem and saved threads. This research found no supported API that transfers this current ChatGPT desktop conversation, plugin connections, browser state or credentials into an arbitrary bridge. Treat that as an unresolved capability, not an implied benefit of using the same account. First-party remote connections explicitly reuse a connected host's chats/tools instead. [App-server guide](https://developers.openai.com/codex/app-server/), [Remote connections](https://learn.chatgpt.com/docs/remote-connections)

## Proposed safety and reliability contract

The following are **design recommendations**, derived from the APIs above and this repository's [AGENTS.md](../../AGENTS.md) and [ADR-025](../decisions/025-repository-boundaries.md); they are not claims about an installed service.

1. **Bound identity and authority.** Allow one numeric Telegram sender ID and one private-chat ID; check both messages and callback queries. Usernames/display names are not the allowlist. Establish IDs through an operator-controlled enrollment process, not “first person to message wins.” Disable groups, attachments and unsupported updates initially. Telegram's user object distinguishes a unique numeric ID from optional username. [User object](https://core.telegram.org/bots/api#user)
2. **Keep secrets outside the agent's readable surface.** Use separate bridge/worker identities or equivalent isolation. The bridge owns the bot token; the worker gets narrowly scoped Codex authentication and approved workspace access. Hard-deny `/home/simon/homelab-private`, ignored credential inventory, SSH agents/keys, root/sudo and deployment credentials unless a later explicit design grants a specific capability. Do not run an internet-fed agent with Simon's full management identity. AGENTS instructions are necessary guidance, not an access-control boundary. Codex distinguishes sandbox enforcement from approval policy; command network restrictions do not cover all MCP/app connections. [Agent approvals/security](https://learn.chatgpt.com/docs/agent-approvals-security)
3. **Make conversation routing explicit.** Persist authorized chat → project/workspace → Codex thread ID, plus active turn and pending request IDs. Show the selected project before accepting work. Start with one active turn per workspace. Queue a new task or explicitly steer the current one; never silently interpret every new message as a new job. A resumed thread restores conversation context, not transactionality or filesystem state.
4. **Scope approvals to a concrete action.** Show the command/diff, working directory, authority requested, task and expiry. Bind a single-use callback to sender/chat/thread/turn/request and the displayed action; reject expired, replayed, resolved or mismatched replies. Do not expose session-wide blanket approvals initially. Questions need their own correlated response path; unsupported forms should stop safely. The release protocol includes server-initiated approvals and user-input requests. [Approval/request protocol](https://github.com/openai/codex/blob/rust-v0.146.0/codex-rs/app-server/README.md#approvals)
5. **Acknowledge durably, then execute.** Telegram confirms updates when a subsequent `getUpdates` offset exceeds their IDs, may redeliver unconfirmed updates, and retains updates at most 24 hours. Persist an inbox record keyed by bot/update ID before advancing the offset; execute from that journal. Do not treat an offset, RPC request ID or received “accepted” reply as exactly-once task execution. [Bot API updates](https://core.telegram.org/bots/api#getting-updates), [Polling FAQ](https://core.telegram.org/bots/faq#long-polling-gives-me-the-same-updates-again-and-again)
6. **Handle uncertainty instead of replaying actions.** Record task, dispatch attempt, thread/turn, completion and outbound reply state. After a crash between dispatch and acknowledgement, reconcile with stored Codex history and actual workspace state; mark ambiguous operations for review. Never automatically rerun deployments or other side effects. Cancellation means “interrupt requested” until completion is observed; it cannot undo already executed commands or remote API calls. On restart, invalidate old approval buttons and require fresh authorization for ambiguous work.
7. **Expire stale commands.** Set a maximum accepted message age and queue length, report discarded tasks, and require confirmation after a long outage. A day-old “restart it” must not suddenly execute after recovery. Keep final checkpoint summaries and repository state for deliberate resume; protect journals/logs/backups as potentially sensitive. Use backoff, health checks, bounded output and explicit failure messages.
8. **Accept the transport's privacy limits.** Telegram cloud chats use client/server encryption and cloud storage; Secret Chats provide a different device-specific end-to-end encrypted mode. Do not treat Bot API chat as a Secret Chat. Prompts and replies traverse Telegram and plaintext reaches the gateway and model; strip secrets and avoid dumping logs/diffs automatically. [Telegram FAQ](https://telegram.org/faq#q-how-are-secret-chats-different), [Privacy policy](https://telegram.org/privacy)

## Existing bridges and dependencies

There are actual Codex-backed projects worth a bounded code review before writing a bridge. `codenoah/codex-telegram-bridge` claims shared local app-server threads, Telegram allowlisting, cancellation and inline command/file approvals. It also documents optional skill installation on first run. `momolm/codex-mainline` claims polling, durable state and supervision, but uses app-server WebSockets. These are project-author descriptions, not evidence of audited security, release compatibility or reliable exactly-once effects. Neither is selected. [Bridge README](https://github.com/codenoah/codex-telegram-bridge), [Mainline README](https://github.com/momolm/codex-mainline)

No new dependency is proposed for installation. Codex is Apache-2.0; the matching Python SDK manifest declares Apache-2.0. Follow-up inspection confirmed that `codenoah/codex-telegram-bridge` declares MIT in its package metadata; this is not a security or compatibility endorsement. Mainline licensing remains unverified. Check the actual pinned release and transitive licences before any adoption; public source availability alone is insufficient. [Codex licence](https://github.com/openai/codex/blob/rust-v0.146.0/LICENSE), [Python metadata](https://github.com/openai/codex/blob/rust-v0.146.0/sdk/python/pyproject.toml), [Bridge package metadata](https://github.com/codenoah/codex-telegram-bridge/blob/main/package.json)

## Follow-up validation and selected design

The interview selected Telegram, necessary diagnostic processing by OpenAI, reviewed operations with scoped approval, and existing-subscription authentication with no API billing fallback. The [implementation plan](codex-messaging-plan.md) records the complete selected boundary and acceptance gates; neither document claims deployment.

The matching SDK launcher copies the parent environment before merging its supplied environment. A supplied allowlist dictionary alone therefore does not remove inherited API keys. Exact-release authentication code enforces `forced_login_method = "chatgpt"`; the service must also control provider/endpoint selection and verify ChatGPT identity before dispatch. Headless/local sign-in mechanics are documented. The separate CI guide's warning about public repositories concerns its copied/persisted-cache workflow; it does not establish a prohibition on this local directly authenticated service working on public code. No copied cache or public CI execution is selected. [SDK launcher](https://github.com/openai/codex/blob/rust-v0.146.0/sdk/python/src/openai_codex/client.py), [Auth enforcement](https://github.com/openai/codex/blob/rust-v0.146.0/codex-rs/login/src/auth/manager.rs), [Authentication](https://developers.openai.com/codex/auth/), [CI authentication guide](https://learn.chatgpt.com/docs/auth/ci-cd-auth)

Independent review did not establish exact-release credential read-denial across every native model tool. The plan therefore makes actual-runtime isolation tests, including process/environment routes, a gate before introducing real account and infrastructure credentials. Read-only mode or a separate worker UID is not sufficient proof. Dynamic tools are experimental and require version-matched event-contract tests. These remain implementation acceptance requirements, not completed tests. [Matching app-server protocol](https://github.com/openai/codex/blob/rust-v0.146.0/codex-rs/app-server/README.md)

## Decisions for the interview

- Is a new Telegram conversation acceptable, or must this existing desktop chat/tools remain available?
- Is Telegram cloud processing acceptable for permitted task content? If not, compare Matrix encryption and first-party remote access before proceeding.
- What may the worker do: read/research, edit/test, commit/push, or administer infrastructure? Which actions require a separate operator channel?
- May one service identity access only a public checkout, or approved local private design too? Credential recovery remains excluded under ADR-025.
- Which account/authentication model and spending/usage limits are acceptable? Which supported host and Codex version will be used?
- One active project/turn initially? What stale-message timeout, outage behavior, journal retention and approval expiry are acceptable?
- Review an existing bridge or build a narrow adapter? Choose language/dependencies only after testing the required approval, user-input, cancellation and recovery paths against the pinned runtime.

Implementation planning should include fault-injection acceptance cases: unauthorized sender and callback, expired approval, duplicate update, crash before/after dispatch, lost completion reply, outage beyond retention, cancellation after a side effect, rate-limit exhaustion, unreadable excluded paths and unavailable authentication. These are proposed future tests; none was run against a deployed gateway.
